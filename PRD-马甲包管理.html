一、背景与目标

本需求为新建菜单「系统管理 - 马甲包管理」（此前不存在），用于管理供推广渠道使用的 APK 马甲包。本期新建该菜单及其列表页与表单框架。

因推广渠道管理侧（安装类型包含 APK 时的「选择马甲包」）当前急需可供选择的成品 APK 包，功能按两期上线：

  • 一期（本次）：搭建菜单与表单框架，仅上线「上传」功能——本地上传成品 APK 包，上传后进入列表，供推广渠道管理「选择马甲包」调用。
  • 二期（后续）：完整打包功能（「新增」入口），不在本文档范围内。
目标：让运营能把现成的 APK 成品包录入系统，即刻成为推广渠道管理的可选马甲包。
版本说明：本文档 v1.x 仅覆盖一期（本地上传）；v2.0 起补充二期（自动打包/「新增」）需求，详见第九节起。一期内容保留作为历史记录，未随二期变更。

二、一期范围与边界

本期做

  • 新建「系统管理 → 马甲包管理」菜单及列表页。
  • 新增「上传」按钮及上传弹窗，支持本地上传单个 .apk 成品包，系统解析包信息并入列表。
  • 上传记录支持「编辑」（可重新上传替换 APK）与「删除」（二次确认 + 关联校验）。
  • 补做推广渠道管理「选择马甲包」与本菜单的联动（见第六节）。

本期不做 / 界面处置

  • 完整打包功能为二期：列表操作区「新增」按钮本期置灰禁用，「操作说明」按钮隐藏。二期已上线该限制已随二期需求解除，详见第十节。
  • 暂仅支持 APK 包类型（二期沿用，未扩展）。
来源区分：上传记录在「备注」栏默认标记 本地上传。原型统一维护在 prototype.html（系统管理 → 马甲包管理）。

三、功能设计

3.1 菜单与入口

新建菜单：系统管理 → 马甲包管理。进入为列表页，含筛选区（地区 / 商户 / 推广渠道 / 打包进度 / 包类型 / 后台显示名称 / 最后操作人 / 创建时间）与数据列表。

列表页右上操作区含「上传」按钮，点击弹出「上传马甲包」弹窗；「新增」按钮本期置灰禁用（二期打包功能），「操作说明」按钮隐藏。

「上传马甲包」弹窗字段如下：

3.3 编辑

列表中本地上传记录的「编辑」操作，弹窗字段与上传弹窗完全一致，并预填该条已有信息（地区、商户、推广渠道、包类型、后台显示名称）。

  • 允许重新上传 APK 包替换：重新选择文件后系统重新解析，回填新的包名称、APP名称（包ID 不变，仍为该记录原有系统 ID）；不重新上传则保留原包信息。
  • 保存后原地更新该行，并刷新「最后操作时间」。
  • 包类型固定 APK 不可改；包名称由解析生成、只读。

3.4 删除

点击「删除」弹出二次确认。确认弹框文案（沿用现有风格）：

标题「温馨提示」；正文「确认是否要删除该条配置信息？」；按钮「取消 / 确定」。

点击「确定」后先做关联校验：检查是否有推广渠道或官方渠道关联了该 APK 包——

  • 无关联：删除该记录。
  • 有关联：不允许删除，提示「该包已被推广渠道或官方渠道关联，不允许删除」，记录保留。

3.5 操作区图标

本地上传记录的操作列含两个图标：✎ 编辑、🗑 删除。图标鼠标移入显示文字说明（「编辑」「删除」）。

列表列结构预留二期打包功能所需的字段与操作（如打包相关图标），本期不实现；本地上传记录不涉及打包，操作仅编辑、删除。

3.6 下载地址交互

列表「下载地址」列显示为省略形式（https://...），并提供：

  • 悬浮完整地址：鼠标移入以浮层显示完整下载地址（如 https://upload-us.q-4-g-r.com/s4/6112906/KK678.com_400196.apk）。
  • 复制图标：地址后置复制图标，点击复制完整地址并提示「链接已复制」。

四、系统解析 APK 与校验

用户选择 APK 文件后，系统对文件进行合法性校验与信息解析：

4.1 解析成功

校验通过后，系统从 APK 解析出包名称、APP名称，并由系统生成包ID、存储生成下载地址，一并回填至记录（表单区提示解析出的包名称 / APP名称，无需人工输入）：

字段来源用途
包名称解析 APK 包名（packageName）列表「包名称」列，如 com.braz.kk678apk。
APP名称解析 APK 应用标签（label）列表「APP名称」列。
包ID系统生成 非 APK 解析列表「包ID」列，记录唯一标识。生成规则：6 位数字，以 100 开头，从 100001 起依次自增（100001、100002、100003…）。编辑重新上传不改变已有包ID。
下载地址系统生成 文件存入对象存储后的 URL列表「下载地址」列，供下载安装与前台调用。
关于「本地上传是否有下载地址」：有。系统接收 APK 后存入服务器 / 对象存储并生成可访问 URL，写入「下载地址」列——即用户 / 推广渠道实际下载安装的地址。
母包版本为二期打包功能相关字段，本地上传记录不适用，该列显示 - -（详见第五节）。

4.2 解析失败

当文件非合法 APK（格式错误、损坏、无法读取包信息等）时，给出错误提示并阻断保存，提示文案示例：解析失败：文件损坏或非合法 APK，请重新上传。用户需重新选择文件方可继续。

六、与推广渠道管理的联动

推广渠道管理中「安装类型」包含 APK 时提供「选择马甲包」入口。本次需求需补做该入口与本菜单的联动。

6.1 联动逻辑

  • 「选择马甲包」下拉的数据源为本菜单的马甲包列表：读取满足匹配条件的 APK 包供选择。
  • 匹配条件：地区、商户一致（推广渠道本期暂未启用，暂不参与匹配）。
  • 下拉项展示「后台显示名称」；选中后带出该包的下载地址与包名称，供渠道安装配置使用。
  • 本菜单上传成功的 APK 包即时可选，无需额外发布操作。
删除约束：已被推广渠道或官方渠道关联的马甲包不允许删除（见 3.4）。参见《PRD · 推广渠道管理模块》。
二期补充：二期「自动打包」建档的记录在「打包完成」之前不进入「选择马甲包」下拉（「待打包」「打包中」「打包失败」状态均不可选），仅当打包成功生成下载地址后才即时加入，规则详见第十三节。

九、二期背景与目标（自动打包）

一期「上传」仅支持录入成品 APK，运营需在系统外自行完成马甲包打包，再上传成品，效率低、依赖人工打包工具。二期在「系统管理 → 马甲包管理」开放「新增」入口，运营可在后台直接建档配置并触发系统自动打包，产出可供推广渠道调用的 APK 马甲包，减少对外部打包工具与人工介入的依赖。

目标：运营只需填写基础信息、上传 APP 图标与启动图（或复用已有配置），即可由系统自动生成马甲包并进入「选择马甲包」可选范围，全程无需离开后台。

十、二期范围与边界

本期做

  • 解除列表操作区「新增」按钮禁用，开放自动打包建档功能；展示「操作说明」按钮（弹窗说明各操作图标含义）。
  • 新增「新增 / 编辑」弹窗，支持填写马甲包配置信息，含「配置选择」——默认配置与读取配置（复用已有配置的 APP 图标与启动图，见第十二节）。
  • 保存后生成「待打包」记录；对「待打包」「打包失败」记录支持点击 🔧 打包 图标触发打包，进入「打包中」后需运营手动点击「↻ 刷新」逐步推进（正在准备打包素材 → 等待打包 → 打包完成），不自动切换。
  • 自动打包建档记录支持「编辑」（复用新增弹窗预填）与「删除」（二次确认 + 关联校验，规则同一期 3.4）。
  • 「推广渠道」在本期正式启用（区别于一期「暂未启用」）：新增弹窗与列表筛选区均提供真实渠道选项。
  • 补充「打包完成」后与「选择马甲包」下拉的联动（见第六节「二期补充」）。

本期不做

  • 「图标工厂」为外部工具入口，本期仅做跳转示意，不接入真实图标生成器。
  • 「打包失败」路径本期不在原型中主动模拟失败场景，仅预留状态与筛选项，交互上默认打包必然成功。
  • 包类型仍暂仅支持 APK，未扩展其他包类型。
一期「上传」功能保留不变，与二期「新增」并列为两个独立入口：「上传」录入本地成品包（无需打包，备注「本地上传」）；「新增」建档后由系统打包（备注「-」，区分来源）。

商户下拉必填选择所属商户号，如「762」；选项随地区联动。
推广渠道下拉必填本期正式启用，选项：官方渠道 / 短信1000 / DALI 5 / DA LI 4 / FB-22 / 106-快手 / 新kwai-快手（与「渠道管理」列表渠道保持一致）；默认选中「官方渠道」。
包类型下拉必填当前选项仅 APK 一项，同一期。
后台显示名称输入框必填运营自定义识别名，全局唯一（校验规则同一期 3.2，编辑排除自身），展示于列表与前台「选择马甲包」下拉。

底部操作：仅一个「保存配置」按钮（无「取消」按钮，点击弹窗右上角「×」关闭）。校验通过后新增记录进入列表，状态为「待打包」（见第十三节）。

十二、配置选择：默认配置 / 读取配置

12.1 默认配置

表单初始默认选中「默认配置」：APP图标、APP启动图均为空（显示「未上传」及空白占位框），需运营重新上传图标压缩包与启动图。

12.2 读取配置

  • 切换为「读取配置」后，右侧出现下拉框，数据源为当前列表中「自动打包」来源的记录（即历史通过「新增」建档的配置，含已打包完成与仍在打包中的记录），下拉默认选中第一项并即时带入。
  • 选中某一已有配置后，带入该配置的 APP图标（压缩包文件名）与 APP启动图（缩略图 + 可预览）；APK包名称同步静默复用该配置本身的包名（即沿用同一「母包」身份），但界面上 APK包名称文本框保持置灰、空白，不展示具体包名，「随机生成」按钮同时禁用、点击不生效——因包名对该记录而言已由所选母包决定，无需也不允许运营改动。
  • APP名称不会被带入，仍需运营手动填写——同一母包（图标/启动图/包名一致）可能对应多个不同 APP名称、不同后台显示名称的马甲包实例。
  • 切回「默认配置」时，已带入的 APP图标、APP启动图将被清空，需重新上传；APK包名称文本框恢复为置灰空白，「随机生成」按钮恢复可用。
  • 若当前列表尚无任何「自动打包」来源记录，切换「读取配置」时提示「暂无可复用的已有配置」，并自动回退为「默认配置」。
「编辑」已有自动打包记录时，表单直接预填该记录自身的 APP图标 / APP启动图（无需通过「读取配置」选择），「配置选择」控件此时不影响已预填内容，仅在需要更换素材时可重新上传覆盖。

十三、打包机制与状态流转

13.1 打包进度状态

状态说明
待打包「新增」保存成功后的初始状态，或「打包中」被取消后回落的状态；母包版本与下载地址均为 - -（直至首次打包完成才生成，见 13.4）。
打包中点击 🔧 打包 图标并二次确认后进入该状态（橙色文字），内部依次经过两个子阶段，见 13.2。进度不自动切换，需运营手动点击「刷新」逐步推进。
打包完成运营在「等待打包」子阶段再次点击「刷新」后完成（绿色文字）。首次由「待打包/打包中」转为「打包完成」时，系统自动生成母包版本与下载地址。
打包失败预留状态与筛选项；本期原型未主动模拟失败场景。

13.2 「打包中」子阶段与备注文案

「打包中」期间，备注列随进程依次显示动态文案（不同于一期「本地上传」备注固定「本地上传」的用法）。子阶段之间不自动切换，全部依赖运营手动点击「↻ 刷新」逐步推进：

阶段备注文案说明
触发打包正在准备打包素材点击 🔧 并二次确认后立即进入，此时长期停留在该阶段，直到运营主动点击「刷新」。
第 1 次点击「刷新」等待打包仍为「打包中」，尚未完成，需再次点击「刷新」才会进入打包完成。
第 2 次点击「刷新」打包完成「打包进度」变为打包完成；该文案打包完成后长期保留在备注列，不会自动恢复为「-」，用于告知运营该条记录已成功产出（除非再次触发打包或取消，见 13.3）。

13.3 操作图标随状态切换 · 取消打包

  • 处于「待打包」「打包完成」「打包失败」（空闲态）时，操作列显示 ✎ 编辑、🔧 打包、🗑 删除 三个图标。
  • 处于「打包中」时，操作列切换为 ↻ 刷新、⊗ 取消 两个图标（编辑/删除在打包中不可用）：
    • ↻ 刷新：手动推进打包子阶段（见 13.2），是「打包中」状态下唯一能让进度前进的操作；不点击刷新，状态会一直停留在当前子阶段，不会超时自动完成。
    • ⊗ 取消：点击后二次确认「确认是否要取消打包？」，可在「打包中」任意子阶段点击，确认后终止本次打包：进度打回待打包，备注显示已取消打包，操作列恢复为空闲态三图标，记录本身保留，可重新点击 🔧 发起打包。
  • 已「打包完成」的记录仍可再次点击 🔧 重新打包（覆盖式演示，会重新经历 13.2 的子阶段与操作图标切换，同样需手动点击「刷新」推进；母包版本/下载地址若已存在则保持不变，不重复生成，见 13.4）。

13.4 母包版本与下载地址生成规则

  • 母包版本：仅在当前值为 - - 时，首次打包完成生成（示意规则：1.0.0.X，X 为随机个位数）。
  • 下载地址：仅在当前值为 - - 时，首次打包完成生成，规则与一期「本地上传」下载地址一致（存储域名 + APP名称 + 包ID 拼接）。
