一、需求背景与范围

提款页现网存在两类问题。布局上，收款信息以展开的表单常驻页面中部，姓名、CPF ID、手机号三个输入框连同区块标题、填写提示、提款规则说明一并堆在金额输入之前，会员每次提款都要滚过一屏已经填好且不可修改的内容才能到达金额区；同时页面文案层层叠加，「提款方式」「收款信息」「提款规则」三段说明实际重复表达同一件事。

逻辑上，现网仅维护一条收款记录。当会员同时具备 CPF 与 PHONE 两种提款方式的条件时，页面落在哪一个没有明确规则，表现为取最后一次保存的那条；会员上次用 PHONE 成功提过款，这次进来可能仍落在 CPF，需要手动切换。本次需求确立一套完整的默认选择规则，使页面总是落在会员最可能要用的那个方式上。

默认选择逻辑按「可用方式 → 信息完整性 → 最近成功提款 → 后台排序值」四级判定页面默认落在哪个提款方式。第六章

四、页面布局调整

4.1 区块顺序与改动对照

提款面板自上而下的区块顺序与改动如下。NEWGPAY 渠道下的区块差异见《NewGPay支付渠道 PRD》第五章，本表以 BESTPAY 渠道为准。

序区块改动前改动后
1账户余额「账户余额：」+ 金额保留。金额展示样式见《钱包一级页改造 PRD》5.7。
2提款需投注投注要求 + 「查看详情 ›」保留，不变。
3渠道区BESTPAY / NEWGPAY保留，不变。
4收款信息展开的表单：区块标题 + 填写提示 + 姓名 / CPF ID / 手机号输入框常驻页面改为一行卡片：左侧标明提款方式（CPF / PHONE），中间为姓名与脱敏后的收款账号，右侧为「切换」。点击整行打开收款信息面板。详见第七章。
5金额输入区输入框 + 「全部」新增清空键，详见 4.2。
6快捷档位三列栅格保留，不变。
7底部结算「您将收到」+ 提交按钮保留。金额展示样式见《钱包一级页改造 PRD》5.7；提交态下底部导航的让位规则见该文档 5.5。

收款信息改为卡片的核心理由：这组信息首次保存后即不可自行修改（见 7.3），此后每次提款它都只是一行需要确认的事实，却以三个输入框的体量常驻在金额输入之前。改为卡片后该区块由约 200px 压缩到约 56px，会员进入页面即可看到金额输入区。

五、提款方式与字段定义

5.1 提款方式

本期提款方式为 CPF 与 PHONE 两种，均为 PIX 收款形态，区别在于使用哪一类 PIX 键。

方式所需字段说明
CPF姓名 + CPF ID以 CPF 号作为 PIX 键收款。
PHONE姓名 + 手机号 + CPF ID以手机号作为 PIX 键收款。CPF ID 仍为必填——它用于实名核验，不因 PIX 键换成手机号而免除。

每个提款方式有三项属性决定它是否出现在会员面前：状态（后台开启或关闭）、解锁（对当前会员是否已解锁）、排序值（展示与兜底排序的权重）。三项均由后台配置，取值与配置入口不在本文档范围。可用指状态开启且已解锁，两个条件缺一不可。

5.2 字段归属与完整性判定

字段归属说明
姓名账户级全局只存一份，两种提款方式共用。
CPF ID账户级全局只存一份，两种提款方式共用。会员的实名标识，与使用哪种 PIX 键无关。
手机号PHONE 方式专属仅 PHONE 方式需要，CPF 方式不采集。

账户级共享带来的连带效果：会员保存 PHONE 方式时会同时填入姓名与 CPF ID，而这两项正是 CPF 方式所需的全部字段——因此保存过 PHONE 方式后，CPF 方式自动判定为信息完整，无需会员再次填写。反之保存 CPF 方式后，PHONE 方式仍缺手机号，不会自动完整。

这一设计避免会员为同一个人填两遍实名信息，也杜绝了两份实名信息填得不一致的风控隐患。代价是「只有一个方式信息完整」这种状态，实际上只会出现在「只保存过 CPF 方式」的会员身上。

信息完整的判定

某提款方式信息完整，当且仅当该方式所需的全部字段均已保存。「已保存」指字段值已写入会员账户并锁定，不含面板内尚未提交的草稿。

已保存的字段CPF 方式PHONE 方式
无不完整不完整
仅姓名不完整不完整
姓名 + CPF ID完整不完整（缺手机号）
姓名 + CPF ID + 手机号完整完整

六、提款地址的默认选择逻辑

会员进入提款页、或在页内把渠道切到 BESTPAY 时执行本判定，决定页面默认落在哪个提款方式、并填入该方式已保存的信息。判定流程见第三章流程图，规则逐条如下。

判定顺序

级判定结果
0取可用的提款方式，按排序值降序排列列表为空 → 进入「暂无可用提款方式」空状态，提交按钮置灰。
1可用方式中信息完整的有几个0 个 → 规则一；1 个 → 规则二；多个 → 规则三。

规则一　没有信息完整的方式

页面进入初始待填写状态：收款信息区显示「添加收款信息」入口，没有卡片。会员点击后打开面板，面板默认选中可用列表中排序值最高的方式。

已保存的字段预填并锁定。例如会员此前只保存过姓名，则打开面板时姓名已填入且不可编辑，只需补填 CPF ID。部分保存的情况按本规则处理——只要还缺字段，就不算完整。

规则二　只有一个方式信息完整

页面默认选中该方式，收款信息区直接显示卡片，卡片内填入该方式已保存的信息。

规则三　多个方式信息完整

条件默认选中
存在成功提款记录取最近一次成功提款所使用的方式。
该方式当前已不可用，或已不完整回退：在其余可用且完整的方式中按排序值取最高。
不存在成功提款记录按排序值取最高。

「成功提款记录」的口径：该提款方式最近一次出款成功的时间。处理中、审核中、审核驳回的订单均不计入——未完成的订单不能代表会员的使用偏好，驳回的订单更不应被当作推荐依据。

兜底用排序值而非保存时间：排序值由运营配置、行为稳定可预测，且不依赖会员数据；而在账户级字段共享的前提下，「自动变完整」的那个方式并没有属于自己的保存时间，用保存时间排序还需额外定义它的取值。

手动切换不写入记忆

会员在页面上手动切换提款方式后，该选择仅在本次停留内生效，不写入记忆。下次进入提款页仍按上述规则重新判定。

这条看似「不听话」，实际自洽：如果会员这次切换后提款成功了，下次自然会因为规则三而默认到它；如果没提成功，说明这次切换未必代表稳定偏好。若另行记忆手动选择，会与规则三产生冲突——记忆的方式和最近成功的方式不一致时，需要再定一套优先级，徒增复杂度。

七、收款信息面板

7.1 三种显示形态

提款面板中收款信息区的显示由「可用方式数量」与「是否有完整信息」共同决定，共三种形态。

形态出现条件展示
空状态可用提款方式数量为 0灰底提示「暂无可用的提款方式，请完成充值后再试或联系客服」。不显示添加入口，提交按钮置灰。
待填写有可用方式，但无信息完整的方式虚线框按钮「＋ 添加收款信息」，点击打开面板。

7.2 面板内交互

面板自底部升起，内容自上而下为：提款方式选择器、对应字段表单、取消与保存两个按钮。

元素要求
方式选择器横向排列全部可用方式，按排序值降序。当前选中项高亮。信息已保存后仍可切换——锁定的是字段值，不是方式的选择权。
切换方式切换后表单按新方式所需字段重绘：账户级字段（姓名、CPF ID）的已保存值保留并保持锁定，方式级字段（手机号）按新方式决定是否出现。
字段顺序CPF 方式：姓名 → CPF ID。PHONE 方式：姓名 → 手机号 → CPF ID。
已保存字段预填入值并置为只读，视觉上与可编辑字段区分，不提供清除。
未保存字段可编辑，带占位符。失焦时做格式校验，错误提示显示在字段下方。
「保存」按钮全部必填字段通过校验前置灰。点击保存后关闭面板、刷新卡片，轻提示「收款信息已填写」。
「取消」按钮关闭面板，丢弃本次未保存的编辑，不改变已保存的值与当前选中的方式。

字段规则未通过时的提示

7.3 保存与锁定

  • 锁定时机：字段在本次提款成功后锁定，而非保存即锁。保存只是写入草稿级的账户信息，会员在首次提款成功前仍可修改。
  • 锁定范围：按字段锁定，不按方式锁定。姓名与 CPF ID 一经锁定，两种方式都读取同一份值。
  • 首次确认：当本次提交会导致字段首次锁定时，提交前弹出二次确认：「请确认提款信息」，正文说明「本次提款成功后，所填写的提款信息将保存至您的账户并不可自行修改。请确认姓名与收款账号准确无误。」，按钮为「返回修改」「确认无误」。
  • 锁定后的修改：会员不可自行修改，需联系客服。前台不提供修改入口，卡片上以锁形标识说明。

八、提交校验与拦截顺序

点击提交按钮后按以下顺序判定，任一环节不通过即中止，不继续后续判定。顺序不可调换——越靠前的条件越是「根本无法提交」，越靠后的越接近「可以提交但需确认」。

序判定不通过时说明
1收款信息是否已填弹窗「请先添加收款信息」
按钮：暂不添加 / 去添加		点「去添加」关闭弹窗并打开收款信息面板。
2是否有未完结的提款弹窗「有未完结的提款」
按钮：关闭 / 查看记录		点「查看记录」进入提款记录页。规则见《提款未完结拦截弹窗 PRD》。
3绑定占用数是否超限轻提示「该 CPF 绑定次数已达上限」或「该手机号绑定次数已达上限」按当前选中方式判定：CPF 方式校验 CPF 绑定数，PHONE 方式校验手机号绑定数。上限由后台配置。
4本次提交是否导致字段首次锁定弹窗「请确认提款信息」
按钮：返回修改 / 确认无误		点「确认无误」继续进入第 5 步；点「返回修改」返回页面不提交。详见 7.3。
5提交二次确认弹窗「确认取款」，列出提款金额、提款方式、收款账号三行，附说明「提交后进入审核，审核通过即按收款账号出款。」点「确认取款」正式提交，轻提示「提交成功，请等待审核」。

金额相关的校验（低于下限、高于上限、超出可提余额）在输入时即时完成并置灰提交按钮，不进入上述顺序。有效流水未达标的校验沿用现行规则。

十、边界与异常处理

场景处理
可用提款方式全部关闭或未解锁收款信息区进入空状态，提交按钮置灰。金额仍可输入，但无法提交。
会员停留期间，某提款方式被后台关闭不打断当前操作。下次执行默认选择判定时按新状态重算；若被关闭的正是当前选中方式，按规则三回退。
最近成功提款的方式已不可用按规则三回退到其余可用且完整的方式中排序值最高的那个。
可用方式仅一个，且信息不完整进入待填写状态。面板内方式选择器仍显示该唯一方式，不可切换。
部分字段已保存（如仅姓名）归入规则一的待填写状态。打开面板时已保存字段预填并锁定，只需补填其余字段。
面板内切换方式后点「取消」丢弃未保存的编辑，并恢复到打开面板前选中的方式，不保留面板内的切换。
字段已锁定，会员仍点开卡片正常打开面板。锁定字段只读展示，可切换方式，可补填该方式缺少的字段。
渠道从 BESTPAY 切到 NEWGPAY整个收款信息区隐藏，NEWGPAY 不采集收款信息。切回时按默认选择规则重新判定。
提交过程中网络失败沿用平台现有处理，保留页面状态与已填金额，不清空。

十一、关联需求同步检查

关联文档同步点处理
《增加Phone提款方式 PRD》该文档定义了 CPF 与 PHONE 两种方式及各自字段，并约定提款信息首次成功后不可自行修改。本文档沿用其字段定义与锁定规则，新增字段归属（账户级 / 方式级）与完整性判定，补齐该文档未定义的多方式默认选择逻辑。
《钱包一级页改造 PRD》5.5 提交态下的导航与返回键、5.6 金额输入框清空键、5.7 金额展示规范。本文档第四章引用，不重复定义。
《NewGPay支付渠道 PRD》第五章定义 NEWGPAY 渠道下隐藏提款方式与收款信息区块。一致，无冲突。本文档的布局调整仅作用于 BESTPAY 渠道。
《提款未完结拦截弹窗 PRD》未完结提款的判定与拦截弹窗。本文档第八章将其纳入拦截顺序的第 2 位，弹窗内容沿用该文档定义。
《提现密码设置优化 PRD》提现密码的校验时机。本次不涉及。若该需求上线，其校验应插入第八章顺序的第 5 步之后。
