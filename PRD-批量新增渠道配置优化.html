批量新增渠道配置优化 · PRD

📄 版本：v1.0 ✏️ 作者：Laura 📅 更新日期：2026-10-03

一、需求概述

推广渠道管理模块的「批量新增渠道」弹窗，当前将「埋点类型」作为整个弹窗的公共字段，选择后展开的专属字段（Pixel ID、访问令牌 TOKEN、test_event_code 事件测试、全渠道回传 kwai ID）同样是公共字段，一次批量创建的所有渠道共用同一份取值。

实际业务中，同一批创建的渠道虽然埋点类型相同，但各自对应不同的广告账户与投放标识，Pixel ID、访问令牌 TOKEN、全渠道回传 kwai ID 均需逐条区分。当前形态下运营只能先批量创建，再进入编辑渠道弹窗逐条修改，批量新增的效率收益被抵消。

本需求将埋点类型的展开字段由弹窗级公共字段下沉为渠道行级字段，使运营在批量新增时即可为每条渠道分别填写；同时按参考平台形态调整弹窗布局。本需求仅调整「批量新增渠道」弹窗，不改变字段的业务含义、校验规则与前台行为。

三、弹窗布局

3.1 顶部公共字段

地区、所属商户、埋点类型三个字段横向并排于弹窗顶部同一行，均为必填。三者作用于本次批量创建的全部渠道。

字段必填控件选项说明
地区必填下拉单选渠道所属运营地区，取值同现有渠道筛选区的地区列表，决定渠道链接的地区归属。
所属商户必填下拉单选渠道归属的商户编号，取值同现有商户列表，决定渠道数据归集到哪个商户。
埋点类型必填下拉单选决定渠道的数据追踪方式与渠道信息表的展开列。可选：常规推广、Facebook API（Facebook服务器接口回传）、TK API（TikTok服务器接口回传）、Kwai API（快手服务器接口回传）、APK上架包、IOS上架包、APK。各类型含义见《推广渠道埋点类型新增 PRD》。
埋点类型由弹窗中部移至顶部，与地区、所属商户同为批量级公共字段；其展开字段则下沉至渠道行，二者的层级在本次调整后不再一致。

3.2 渠道信息表

渠道信息区为一个表格：表头为列名，其下每一行对应一条待创建的渠道，所有字段按行独立填写。列的组成由顶部「埋点类型」决定（见 3.3）。

当列的总宽超出弹窗可视区时，表格区域出现横向滚动条，运营横向滚动查看与填写右侧列；表头随内容一同横向滚动。增删行按钮固定在表格右侧、不属于滚动区域，横向滚动时始终可见可点。

3.3 列组成规则

渠道名称、落地指向、跳转域名、推广商为基础列，任何埋点类型下均展示。其余列按埋点类型动态增减，即原「埋点类型展开字段」下沉后的形态。

常规推广渠道名称、落地指向、跳转域名、推广商
Facebook API（Facebook服务器接口回传）
TK API（TikTok服务器接口回传）
Kwai API（快手服务器接口回传）		渠道名称、落地指向、跳转域名、推广商、Pixel ID、访问令牌TOKEN、test_event_code事件测试

3.4 字段说明

字段（列）必填控件展示条件选项说明
渠道名称必填文本输入始终展示该条渠道的名称，用于后台列表识别与报表维度展示，同一商户下不可重复。
落地指向必填下拉单选始终展示渠道链接被访问后落地的页面。可选：仿谷歌页、官网首页、官网注册页、主域名、防封下载页。
跳转域名必填下拉单选始终展示渠道链接实际跳转使用的域名，取值为当前地区已配置的可用域名。
推广商必填下拉单选始终展示该条渠道归属的推广商，用于按推广商归集渠道效果数据。
Pixel ID必填文本输入埋点类型为 Facebook API / TK API / Kwai API 时展示三方广告平台的像素标识，由投流方提供，用于该条渠道的事件回传定位。各条渠道可填写不同取值。
访问令牌TOKEN必填文本输入同上调用三方平台回传接口的鉴权令牌，与 Pixel ID 成对使用，由投流方提供。各条渠道可填写不同取值。
test_event_code事件测试非必填文本输入同上三方平台的测试事件码，仅在联调验证回传链路时填写。填写后回传事件进入三方平台的测试事件流，不计入正式数据，测试完成后须清空。
全渠道回传kwai ID非必填文本输入埋点类型为 APK上架包 时展示该上架包全渠道数据回传至快手平台的标识，由投流方提供。留空表示不做快手全渠道回传，不影响该渠道在我方后台的数据统计。

埋点类型为 Facebook API / TK API / Kwai API 时，渠道信息表下方展示红色提示文案：test_event_code事件测试：仅供测试使用，测试完成后注意删除该输入框填入的内容。其余埋点类型下不展示该提示。

3.5 增删行

操作交互说明
默认行数打开弹窗时默认展示 2 行空白渠道。
新增行（+）在列表末尾追加一行空白渠道，列组成与当前埋点类型一致，已填写行的内容不受影响。
删除行（−）删除该按钮所在行。当前仅剩 2 行时点击删除，提示「至少需要创建两个渠道」且不执行删除。
按钮位置固定于渠道信息表右侧，不随表格横向滚动移动，始终与所在行水平对齐。

四、切换埋点类型的处理

运营在已填写部分内容后切换顶部「埋点类型」，渠道信息表按新类型重建列，此时各行已填内容按下述规则处理。

内容处理说明
基础列（渠道名称、落地指向、跳转域名、推广商）保留四列在任何埋点类型下均存在，各行已填 / 已选取值原样保留。
新旧类型共有的展开列保留如在 Facebook API 与 TK API 之间切换，Pixel ID、访问令牌 TOKEN、test_event_code 事件测试三列的各行取值原样保留。
新类型不存在的展开列清空切换后该列不再展示，其内容一并丢弃；再切回原类型时该列为空，需重新填写。
新类型新增的展开列空值各行均为空，由运营填写。
行数保留切换前已增删的行数维持不变，不重置为默认 2 行。
切换埋点类型会丢弃新类型不存在的展开列内容，且无二次确认。运营应先确定埋点类型再填写渠道信息。

五、保存

项说明
校验时机点击「确定」时统一校验全部行。
校验内容逐行校验各必填列是否已填写，规则与「新增渠道」弹窗对应字段一致。任一行校验不通过则不提交，定位到首个不通过的行与列并提示。
保存结果校验通过后按行创建渠道，每条渠道的埋点类型、地区、所属商户及渠道设置取自弹窗公共字段，其余字段取自该渠道所在行。

六、关联需求同步

本需求与《推广渠道埋点类型新增 PRD》存在口径交叉，两份文档需同步：

  1. 该 PRD 2.5 节「影响范围」描述新增渠道、编辑渠道、批量新增渠道三个弹窗的渠道设置字段一致。本需求实施后，批量新增渠道弹窗中埋点类型的展开字段改为按行配置，与另两个弹窗的层级不再一致；该 PRD 2.5 节相应表述需同步修订为「批量新增渠道弹窗的埋点类型展开字段按渠道行配置，详见《批量新增渠道配置优化 PRD》」。
  2. 该 PRD 2.2 节定义的「全渠道回传 kwai ID」、2.3 节定义的事件说明入口，字段含义与展示条件在本需求下均不变，仅批量新增场景的录入位置由弹窗级变为行级。
  3. 后续若新增埋点类型并带有专属展开字段，需同步在本需求的渠道信息表中补充对应列与列组成规则。

七、验收要点

  1. 布局：批量新增渠道弹窗顶部地区、所属商户、埋点类型三字段同行并排展示，均带必填标识。
  2. 列组成：常规推广、IOS上架包、APK 下渠道信息表为 4 列；Facebook API / TK API / Kwai API 下为 7 列，增加 Pixel ID、访问令牌 TOKEN、test_event_code 事件测试；APK上架包下为 5 列，增加全渠道回传 kwai ID。
  3. 按行填写：同一批次内各行的 Pixel ID、访问令牌 TOKEN、test_event_code 事件测试、全渠道回传 kwai ID 可填写互不相同的取值，保存后在渠道列表与编辑渠道弹窗中回显为各自取值。
  4. 横向滚动：列数超出可视区时渠道信息表出现横向滚动条，表头与数据行同步滚动；增删行按钮固定在表格右侧，滚动过程中始终可见且与所在行对齐。
  5. 增删行：默认 2 行；点击 + 追加的新行列组成与当前埋点类型一致；仅剩 2 行时点击 − 提示「至少需要创建两个渠道」且不删除；删除中间行时其余行内容不发生错位。
  6. 切换埋点类型：基础列与新旧共有展开列的各行取值保留，新类型不存在的展开列内容清空，行数不重置。
  7. 红色提示：Facebook API / TK API / Kwai API 下渠道信息表下方展示 test_event_code 提示文案，其余埋点类型下不展示。
  8. 回归：渠道设置区的安卓 / 苹果 Tab 切换及其下全部字段的联动展开正常；新增渠道、编辑渠道弹窗的埋点类型展开字段与事件说明不受影响；批量保存后的渠道在渠道列表、测试回传弹窗与推广效果报表中展示正常。
